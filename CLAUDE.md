# laravel-campaigns

Lets AI agents run a Laravel app's email marketing on the app's own server. The app keeps its lists (dynamic ones fed from its own users, static ones for other contacts), its subscribers and an append-only record of every consent change; campaigns go out one message at a time through Mailgun on the app's own queue, at a pace set per campaign; and the provider's feedback stops addresses that bounce, complain or unsubscribe. Agents reach it through an MCP server the package adds to the app. There are no screens: every operation is a package action, so a later UI can call the same code.

The package is still being built. Today it has the config, the data model, the provider interface, subscriptions (the consent actions, the consent records, dynamic lists kept in step with the app's records, and the sync command) and the pages an email's links open: unsubscribe, with the mail apps' one-click, and the double opt-in confirmation with its email; imports from other systems, the engagement tiers and the sunset, the built-in subscriber filters, and the app's named audiences and read-only resources; templates and campaign emails kept as numbered revisions, the package's starter template, the rules every revision meets and the renderer that fills an email's placeholders; upload links and their files, emails uploaded as HTML or a zip with their images, the asset library, the guard every server-side fetch passes, and the pre-send checks; campaigns made from a template, an upload or inline content, their settings, audiences and saved audiences, the audience preview, starting or scheduling (the audience frozen into messages in the send order, the email frozen with UTM tags), pausing, resuming, cancelling and changing the pace; the sending provider with its Mailgun driver and a fake, the email one recipient gets, test emails to the app's test addresses, and the web version of an email; the pump that hands each sending campaign's messages to the queue at its pace, and the job that sends one. Feedback and the MCP server come next.

## Architecture

- `src/CampaignsServiceProvider.php`: the config (re-merged so a published file picks up new nested keys), the views, translations and route file, the migration stub, the install command (config and migration), the commands, the morph aliases, the `campaigns.links` rate limiter and the pump's schedule.
- `config/campaigns.php`: the `enabled` switch, the links' base URL, the name the pages and emails call the app, the sending provider, the countries whose opens are never tracked, the mailer, sender, reply-to address and marketing domain of campaigns and the package's emails, the footer's postal address and privacy link, the alert address, the addresses test emails may go to, the default language of an email, the asset library's disk and image limit, the uploads' private disk and size limit, the pre-send checks, the UTM tags and the hosts that get them, the queue, the cache store for the scheduled commands' locks, whether the package schedules its commands, the list sources, audiences and resources an app registers, the engagement windows and sunset period, the fallback pace, the per-domain daily caps and the stop-loss thresholds.
- `database/migrations/create_campaigns_tables.php.stub`: every table, in one stub.
- `src/Models/`: `CampaignList` and `Subscription` (a subscriber's place on a list), `Subscriber` (one address, optionally linked to an app record through the `subscribable` morph), `ConsentRecord` (the ledger), `Campaign`, `CampaignMessage` (one campaign's email to one subscriber), `TestSend`, `ProviderEvent` (what the provider reported), `ApiToken`, `Template` (a reusable email), `Revision` and `RevisionContent` (one version of a template's or campaign's email, and its content per locale; `Models\Concerns\HasRevisions` gives both owners `revisions()` and `currentRevision()`), `Asset` (an image in the asset library), `Upload` (a file sent through a one-time link) and `SavedAudience` (a named set of filters).
- `src/Content/`: an email's content and how it becomes a recipient's email. `EmailContent` (one locale's subject, preheader, HTML and text, as given), `ContentRules` (what every revision must meet, and its plain text generated when none was given), `Renderer` (fills the placeholders for a `Personalization`, giving a `RenderedEmail`), `Placeholders` (the fixed set and the one-pass replacement), `PlainText` (text from HTML), `Html` (reads HTML, never writes it) and `Locales` (the default language).
- `src/Templates/StarterTemplates.php`, `resources/templates/`: the package's starter templates, read-only files beside the app's own templates.
- `resources/views/mail/footer.blade.php`, `footer-text.blade.php`: what `{{footer}}` becomes in the HTML and the text.
- `src/Enums/`: the statuses, kinds, bases, actions and reasons the models cast to.
- `src/Contracts/CampaignProvider.php`: the sending provider (send one message, verify and parse webhooks, fetch logged events and suppressions), with its value objects in `src/Sending/`. `campaigns.provider` picks it (bound as a singleton): `Sending\MailgunProvider` (sends through the campaigns mailer as `Mail\CampaignEmail`; its feedback methods come with the webhooks) or `Sending\FakeProvider`. A send that isn't accepted throws `Sending\SendFailed` with a `SendFailure` (`NotAccepted`, `DomainRefused`, `Unclear`).
- `src/Sending/MessageComposer.php`: one recipient's email from the token of its links (`outgoing()` for the provider, `rendered()` for the web version), for a campaign's message or a test email. `OutgoingMessage::headers()` makes the headers a send carries (one-click unsubscribe), which `Mail\CampaignEmail` and `toEmail()`, the pre-send spam check's message, both use; From, Reply-To and the subject come from the same `OutgoingMessage` in both.
- `src/Actions/`: every change to a subscriber, one class each, each writing its consent record: `SubscribeAction` (also the resubscribe, when the person asked), `DeclineAction` (an unticked sign-up box), `ConfirmSubscriptionAction`, `RemoveFromListAction`, `OptOutAction` (what an unsubscribe does), `OptInAction`, `BlockAction`, `UnblockAction`, `ChangeEmailAction`, `ForgetSubscriberAction` (a deleted record), `SyncRecordAction` (one record onto its dynamic list), `UnsubscribeAction` (a person's unsubscribe from an email: the opt-out plus the email's `unsubscribed_at`), `ResubscribeAction` ("subscribe again" from an email), `SendConfirmationAction` (queues a double opt-in's email) and `ImportContactsAction` (contacts, opt-outs, blocks and engagement from another system, a dry run or for real, its rows in `src/Imports/`). Templates and emails: `CreateTemplateAction`, `DuplicateTemplateAction` (from a template or a starter), `UpdateTemplateAction` (name, description, default mark), `ArchiveTemplateAction`, `AddRevisionAction` (a template's or a draft campaign's new version) and `RestoreRevisionAction`. Campaigns: `CreateCampaignAction` (from an `EmailSource`: a template, a starter, an upload or inline content; returns a `CreatedCampaign`), `UpdateCampaignAction` (a draft's settings, checked by `Support\CampaignSettings`), `DuplicateCampaignAction`, `StartCampaignAction` (now or at a time; claims the draft and queues `Jobs\FreezeCampaignJob`, which runs `FreezeCampaignAction`), `PauseCampaignAction`, `ResumeCampaignAction`, `CancelCampaignAction`, `ChangePaceAction` (a slow-down or a speed-up), `QueueCampaignChecksAction`; `SaveAudienceAction` and `SetCustomFieldsAction`. A later UI or MCP tool calls these; it never writes the models itself.
- `routes/campaigns.php`, `src/Http/`: the pages an email's links open, `/campaigns/u/{token}` (unsubscribe, preferences and one-click), `/campaigns/c/{token}` (confirmation) and `/campaigns/v/{token}` (the web version), with their controllers and `PageHeaders`; views and English strings in `resources/`.
- `src/Actions/SendTestAction.php`, `src/Jobs/SendTestJob.php`, `src/Support/TestAddresses.php`: test emails of a campaign's or a template's email, to `campaigns.test_addresses` only.
- `src/Jobs/SendConfirmationJob.php`, `src/Mail/ConfirmSubscriptionMail.php`: the double opt-in email, sent from the job that makes its link.
- Uploads: `CreateUploadAction` (a one-time link's row), `ReceiveUploadAction` (the file, onto the private `campaigns.uploads.disk`), `ClaimUploadAction` (once, by the tool of its `UploadPurpose`), `PruneUploadsAction` (expired rows and their files); `ReadEmailUploadAction` reads an email upload through `Uploads\EmailArchive` (one HTML file or a zip) into an `Uploads\EmailUpload`, and `AddUploadedRevisionAction` saves it as a revision with its images (`Uploads\UploadedRevision`). `Content\ImageReferences` finds relative image paths and swaps them in the source string.
- `src/Assets/`: `ImageFile` (an image checked by its bytes) and `AssetLibrary` (stores images on `campaigns.assets.disk` and gives their addresses); `AddImageAction` (bytes) and `AddImageFromUrlAction` (an https address) add one.
- `src/Fetching/`: `Fetcher`, the one way the server requests an address an agent gave (links, images), with `PublicAddress` (which IPs may be fetched), `HostResolver` (DNS, bound in the container) and `StaticHostResolver` (fixed answers for tests).
- `src/Checks/PreSendChecks.php`, `Actions\QueueChecksAction`, `Jobs\RunChecksJob`: the checks run on a revision before it is sent, queued, their results stored on the revision.
- `src/Support/Token.php` (a link's token and its hash), `Links.php` (the addresses put in emails), `PageLocale.php` (a subscriber's language and text direction), `Sender.php` (who campaigns come from, and the marketing domain), `Keys.php` (the keys templates and the like are named by), `TextValue.php` (a short text an agent gives, checked before it reaches a column).
- `src/Support/ConsentContext.php`: who changed someone's consent and how (source, basis, notice version, the person's choice, IP and browser), passed to every action. `src/Support/EmailAddress.php`: the one place an address is cleaned and validated; `SubscriberDetails.php` the one place a subscriber's name, locale, timezone and country are.
- `src/Support/Engagement.php`: the engagement tiers (`EngagementTier`) and the sunset, for a subscriber in hand and for a query, behind `Subscriber::tier()`, `isSunset()`, `isMailable()` and the `mailable` scope.
- `src/Audiences/SubscriberFilters.php`: the built-in filters (lists, locales, countries, tiers, opted out, blocked, sunset, custom fields, dates, and what someone did with an earlier campaign), read from and written back to a plain array, applied to a subscriber query.
- `src/Audiences/AudienceDefinition.php` (who a campaign goes to within its lists, as an agent gives it and as the campaign stores it), `CampaignAudience.php` (the one query behind the preview, the start's count and the freeze) and `AudiencePreview.php` (the preview's counts).
- `src/Actions/PumpCampaignsAction.php` (run by `src/Commands/PumpCommand.php`, `campaigns:pump`, every minute): starts scheduled campaigns whose time came, hands back starts whose freeze was lost, completes campaigns with nothing left, and claims each sending campaign's next messages, one `Jobs\SendMessageJob` each; `Sending\PumpResult` is what a run did. `src/Sending/Allowance.php`: how many a campaign may claim now. `src/Jobs/SendMessageJob.php`: sends one claimed message and acts on the provider's answer.
- `src/Sending/Pace.php`: a campaign's pace, its checks, its config fallbacks, whether a change sends faster, a day's volume and the sending hours. `src/Content/UtmTags.php`: the UTM tags a start adds to links to the app's own sites. `src/Enums/MailboxProvider.php`: an address's mailbox provider, read from its domain, for the send order and the breakdowns.
- `src/Events/`: `CampaignStartedEvent`, `CampaignPausedEvent` and `CampaignCompletedEvent`, dispatched after commit, and `CampaignQueueStalledEvent`.
- `src/Contracts/Audience.php`, `src/Contracts/AgentResource.php`: an app's named audiences (`campaigns.audiences`) and the read-only data agents may read (`campaigns.resources`), resolved through the `Campaigns` manager.
- `src/Contracts/ListSource.php`, `src/Concerns/HasCampaignSubscriber.php`, `src/Observers/ListSourceObserver.php`: an app record behind a dynamic list (configured in `campaigns.list_sources`), the trait its model uses, and the events that keep the list in step.
- `src/Campaigns.php` (facade `Facades\Campaigns`): the list sources, the dynamic list rows, the consent context a record is created under, the audiences (`audienceSubscribers()` turns one into a subscriber query) and resources, `recordActivity()`, and `name()`, what the pages and emails call the app.
- `src/Commands/SyncListCommand.php`: `campaigns:sync-list <list>`, a dry run unless `--force`, `--id` for one record. `src/Commands/PumpCommand.php`: `campaigns:pump`.
- `database/factories/`: a factory per model, autoloaded with `src/` so apps can use them in their own tests.

## Key design decisions

- **`laravel/framework`, not the `illuminate/*` components.** The package is shaped like an app (routes, views, mail, queued jobs, the scheduler, signed links), and its jobs, events and pages need the foundation's helpers and traits. Checkers that prefer the split components flag it; it is deliberate.
- **MySQL, MariaDB, PostgreSQL and SQLite.** SQL Server isn't supported: its unique indexes allow a single NULL, and several nullable columns here are unique.
- **One migration stub, no `down()`.** Until the first version is tagged, schema changes edit `create_campaigns_tables.php.stub` in place. After that, every change is a new, additive stub, since apps have already published and run the old one.
- **Every string column has an explicit length** (addresses 254, user agents `text`): apps often lower Laravel's default string length, and a 254-character address must fit. Tests run with a default length of 125, so an unsized column fails the column-length test on MySQL and PostgreSQL.
- **Every foreign key has its own index**, since PostgreSQL adds none, and JSON columns are `jsonb` (`json` on MySQL), since PostgreSQL can't compare plain `json` in a `DISTINCT`.
- **The subscriber's address compares bytes on MySQL and MariaDB** (`utf8mb4_bin`): their default collations make `josé@` and `jose@` one value, which would break the unique index. Addresses are stored lower-cased, so case needs no help from the collation.
- **One subscriber per app record**: the `subscribable` morph pair is unique, so an address change that moves an account to an existing subscriber unlinks the old row first. The morph id column follows the app's `Schema::morphUsingUuids()` or `morphUsingUlids()`, which must be called before the migration runs.
- **`custom_fields`, not `attributes`,** for a subscriber's free-form data: a column called `attributes` collides with Eloquent's own `$attributes` property inside the model.
- **Morph aliases carry a `campaigns.` prefix** and are registered with `Relation::morphMap()`, never `enforceMorphMap()`: apps that enforce a morph map need the aliases, and enforcing is the app's decision.
- **Records outlive their subscriber.** Consent records and campaign messages keep their row with `subscriber_id` nulled when a subscriber is deleted, so what someone agreed to and a campaign's numbers survive; list subscriptions cascade. The address on those messages is personal data, so the code that deletes a subscriber must clear it too.
- **A revision never changes once saved** (only its check results do): every edit adds one, numbered after the last under a lock on its owner's row, the last number read with a locking read (a plain one would see an older snapshot inside a caller's MySQL transaction), with a unique index behind it; the current one is the highest number, and restoring an old one adds a copy of it, so the history keeps every version in the order it was current. A campaign's email changes only while the campaign is a draft, read from the row under that lock. The revision's morph id is an integer column, not `morphs()`, which would follow an app's `morphUsingUuids()` while the owners are always the package's own integer-keyed models.
- **An email's HTML and text are `mediumText`**: MySQL's `text` holds 64 KB, under the 90 KB an email may have.
- **Placeholders are a fixed set, replaced in one pass and never compiled** (`Content\Placeholders`): uploaded Blade would run code, and a value put in (a first name of `{{footer}}`) is never read as a placeholder again. Values go into the HTML escaped (entities and all, since a value is text) and into the text as they are, while an author's fallback is HTML whose entities stay; a subject or preheader holds only `{{first_name}}`, `{{name}}` and `{{email}}`, filled raw with control characters turned to spaces, since the subject becomes a mail header. `{{unsubscribe_url}}` and `{{preferences_url}}` are one address (one page serves both). `{{preheader}}` places the preheader; an HTML that doesn't place it gets it in a hidden block right after `<body>`.
- **What every revision meets** (`Content\ContentRules`), all problems reported at once: the default language present (`campaigns.locale`, which the service provider fills from `app.locale` at registration, since `App::setLocale()` rewrites `app.locale` for each visitor); no language given twice, however written (`EN`, `pt-br`); a subject on one line; nothing in double braces that isn't a known placeholder (`{{frist_name}}`, `{{first-name}}`, `{{ $name }}`), since it would reach every inbox as written; an unsubscribe link in the HTML and in the text each (`{{unsubscribe_url}}`, `{{preferences_url}}` or `{{footer}}`, which carries it), a generated text included; every image on `https` (`img` `src` and `srcset`, `background` attributes, and CSS `url()` read from style attributes and `<style>` elements as the DOM decodes them, never from the raw HTML, where `&quot;` quotes and body text would mislead); at most 90 KB of HTML once rendered with sample values as long as real ones, since Gmail clips at 102 KB and click tracking lengthens links, and at most 90 KB of plain text.
- **A NOT NULL timestamp gets a default** (`useCurrent()`), as `campaign_uploads.expires_at` does: on a MySQL or MariaDB server without `explicit_defaults_for_timestamp`, the table's first timestamp without one silently becomes `ON UPDATE CURRENT_TIMESTAMP`.
- **HTML is read through the DOM but changed as a string** (`Content\Html`): libxml writes `{` and `}` in an `href` or `src` back out percent-encoded, which breaks the placeholders.
- **The footer renders in the email's language** when the package's strings exist in it (`PageLocale::pick()`), the app's language put back afterwards (`Localizable`), so a queued job never leaves the app in another language.
- **Starter templates are files, not rows** (`Templates\StarterTemplates`): a package update changes them without touching an app's templates, and their keys are reserved so a key names one template.
- **Every server-side request to an address an agent gave goes through `Fetching\Fetcher`**: each hop, redirects included, must name a host whose every resolved address is public (`PublicAddress`: PHP's global-range filter plus multicast and NAT64, which it lets through), the request goes to the host exactly as checked (`Fetcher::addressOf()`: a trailing dot or a Unicode name would make curl look the host up again by itself), the connection is pinned to the checked address with curl's `CURLOPT_RESOLVE`, no proxy is used (a proxy resolves the host itself), and redirects are followed by the fetcher, never the client. A host name must end in a label that starts with a letter, so a number curl reads as an IP (`2130706433`, `0x7f.1`) is never a host; user details and backslashes are refused, since PHP and curl parse them differently. A refusal never names the private address, since the results reach whoever runs the checks. The body is asked for uncompressed and never decoded (a compressed one would expand past the limit), the headers callback stops one declared too large, the progress callback stops one that grows past it (Guzzle 8 only: Guzzle 7 ignores its answer, so there a body without a declared length runs to the 10-second timeout into a temporary file), and only the limit is ever read into memory. The proxy option is the empty string, which every Guzzle 7 and 8 turns into "no proxy"; a `no` list would let Guzzle 7.9 and older hand the choice back to curl's environment. Pass no other curl option without checking it against Guzzle 8's allow-list (it refuses `CURLOPT_MAXFILESIZE_LARGE`, for one), and never Guzzle's `stream` option, which switches to the stream handler and ignores the curl options. `Http::fake()` skips curl, so a test sends `Fetcher::options()` through the real client to a pinned closed port and expects curl's error 7.
- **Assets are named by their content** (`campaigns/assets/<sha256>.<ext>`, unique on disk and path): an image's address is known before it is stored, and the same image uploaded again is the asset already there. The type, extension and content type come from the bytes (`getimagesizefromstring`: JPEG, PNG, GIF, WebP), never the name; SVG is refused, since it can carry script on the app's origin. Nothing is ever deleted, as delivered mail keeps loading the images, so an upload is checked whole (the zip, the images, the revision rules) before any image is stored.
- **An upload waits on a private disk** (`campaigns.uploads.disk`), since it may hold an unsent email or a list of contacts. Its link takes one file within 15 minutes, counted on the bytes as they arrive; the file then waits a day (`expires_at` serves both), and the tool of its purpose claims it once with a conditional update, then deletes it. An upload refusal's exception code is the HTTP status the endpoint answers with (404, 409, 410, 413, 400, 422, and 500 when storing failed). `PruneUploadsAction` deletes expired uploads and any older file no upload names.
- **A zip is never unpacked to disk**: it is opened from a temporary copy and its files read into memory, and it holds only `email.html`, `email.txt`, `translations/<locale>.html` and `.txt`, and `images/`: no `..`, absolute path, link or encrypted entry, no name twice, no second version in the default language, at most 200 files and 50 MB unpacked. Each file is read to its declared size and refused when its bytes differ, never to the limit, since PHP reserves the whole length asked for. One folder wrapping everything is stepped into, and the files zip tools add (`__MACOSX/`, `.DS_Store`, `Thumbs.db`) are skipped and not counted. A relative image path resolves from its own file's folder, then the zip's root, `..` never climbing above it. A version's subject is the one given for its locale, else its `<title>`.
- **Pre-send checks report; they never block** (only the revision rules refuse). They are queued (`QueueChecksAction`), since fetching every link outlasts a tool call, and `RunChecksJob` stores them on the revision only while its run is still the latest. `check_results` is `{status: queued, run, queued_at}` while waiting, `{status: done, run, queued_at, finished_at, passed, failed, checks: [{check, locale, status: passed|failed|skipped, message, ...}]}` once run, and `{status: failed, run, queued_at, finished_at, message}` when the job died; the checks are `locales` (`missing`), `unsubscribe`, `privacy_link`, `size` (`bytes`, counting 400 bytes for each tracked link), `images` (`items`), `links` (`checked`, `items` of `url`, `problem`, `locales`) and `spam_score` (`score`, `rules`). A link is fetched with a GET stopped once its headers arrive (some servers refuse HEAD, and no page is read); the package's own token pages are left out; the links stop after 100 addresses or 120 seconds and the whole run after 240, under the job's 300-second timeout. The spam score sends the email, filled with sample values and the headers a send carries, to Postmark's free checker, and is skipped with a note when it is off or the checker doesn't answer.
- **Campaigns come from the marketing domain** (`Support\Sender`): `campaigns.mail.domain`, else the sender's domain; the sender is `campaigns.mail.from`, else the campaigns mailer's `from`, else the app's, and a missing domain is an error that names what to set.
- **The pace's state the ledger can't give is in columns** (`campaigns.pace_started_at`, `rate_halved_until`), never in the cache, which a release clears.
- **Tokens are stored as SHA-256 hashes only** (`token_hash`, `confirm_token_hash`, `signature_token_hash`) and are `$hidden` on their models; the raw token exists only in the email or response that carries it.
- **Sending is off by default** (`campaigns.enabled`): an app installs the package, records consent and builds its lists before anything can send.
- **A message moves back from `sending` only when the provider said it took nothing** (`NotAccepted`, `DomainRefused`), since otherwise the provider may already have the email; the other step back is `queued` to `pending`, for a claim whose job never sent it (`MessageStatus`). Either step back clears `claim_id`, `claimed_at`, `sending_at` and `token_hash`, so the pace counts the message as never sent and its next claim starts afresh. A campaign holds one message per subscriber (a unique index on the pair).
- **One app-wide opt-out.** A person's unsubscribe (and an unticked sign-up box) sets the subscriber's `opted_out_at`, which stops all marketing whatever lists they are on; their list subscriptions stay, for targeting and history. A block (`blocked_at`) is a fact about the address, never cleared by anything but `UnblockAction`.
- **Only the person clears an opt-out**: a context with `accepted: true` (a ticked box, the switch, subscribing again) or a confirmed double opt-in. A sync, an import or an agent adding a contact never does: `SubscribeAction` leaves an existing subscription and the opt-out as they are.
- **List statuses**: `pending` waits for a double opt-in; `unsubscribed` means a dynamic list's record can't be on it right now: not eligible, or no address that can be synced (no valid address, or one another record holds). It flips back once the record can be, with no consent record either way, since neither is a consent change. While it is off, the address its subscriber still holds isn't mailed through that list (its static lists still reach it). An agent taking someone off a static list deletes the row, so adding them again starts afresh.
- **Every state change is a conditional update** (`whereNull('opted_out_at')` and so on), and its consent record is written only when the update changed a row, so two requests racing never record one change twice.
- **Leaving keeps a suppressed address.** A deleted record, or an address the person moved away from, keeps its row stripped to the address when it is blocked or opted out, so a later import can't mail it again; any other address is deleted. Either way the person's details, IPs, browsers and the addresses on their sent mail go, and their pending mail is skipped (`ForgetSubscriberAction`), except the sent mail an address change moves to the person's new row, which keeps the old address.
- **An address change moves the person, not the block** (`ChangeEmailAction`): in place when the old row holds nothing to keep; otherwise the person moves to the new address's row (made, or one that exists, the stricter list status winning), their consent records follow them except block and unblock, and the old row is forgotten. The record link moves first, since the morph pair is unique.
- **The observer never throws**, but for one case. A failure syncing a record (a broken list source in the config included) is reported and rolled back to its own savepoint, so an app's sign-up can't fail because of its marketing list; `campaigns:sync-list` repairs what was missed. The exception is a deadlock or lock timeout inside the app's transaction: Laravel rolls back no savepoint then and the database has ended or aborted the whole transaction, so it is rethrown.
- **A consent context is scoped** to one model class and one callback (`Model::withCampaignConsent()`), restored in `finally`, and the manager is a scoped binding, so it can't leak into the next record, request or job. A record made without one counts as made by staff.
- **Records older than their list are legacy.** The dynamic list's row is created the first time it is needed, and the sync gives records created before it the `legacy` basis.
- **The sync's dry run is the real run rolled back**, one transaction per record, so its counts are what `--force` would do, except where one record's change makes room for another's (two records sharing an address both count as new; a record moving to an address another is leaving counts as not synced).
- **Rows other requests may make at the same moment go through `Support\Rows::firstOrCreate()`**, never Eloquent's `firstOrCreate()`/`createOrFirst()`: after a lost insert race those read the row with a plain select, which inside a MySQL transaction returns the snapshot taken before the row existed, and throw. `Rows` reads it with `sharedLock()`, never `lockForUpdate()`: the failed insert already holds a shared lock, and two losers asking for exclusive ones deadlock each other.
- **A choice made at creation is recorded even when the record isn't eligible yet** (it joins, then leaves until eligible), so a later sync never subscribes someone who left the box unticked.
- **Nobody is added to or taken off a dynamic list by hand**: `SubscribeAction` refuses a subscriber no record stands behind and `RemoveFromListAction` refuses the list, since the record's next save would undo either. The app's records and `isEligible()` decide it.
- **The pages run outside the app's `web` middleware**: a mail app's one-click unsubscribe (RFC 8058) posts with no cookies or CSRF token and must get a plain 200, never a redirect. They set no cookie and use no session, so their views carry no `@csrf`.
- **Opening a link changes nothing; only a POST does**, since link scanners open every link in an email. That holds for the confirmation link too, so a scanner can't confirm an address for someone who never asked.
- **One page for unsubscribe and preferences**: `/campaigns/u/{token}` shows the person's state (subscribed: unsubscribe from everything; opted out: subscribe again; blocked or forgotten: nothing to do). The paths are fixed, since delivered mail points at them, and apps redact `/campaigns/u/`, `/campaigns/c/` and `/campaigns/v/` (each carries a token) from error reports.
- **A link's token resolves to the email it came in** (`campaign_messages.token_hash`, else `campaign_test_sends.token_hash`), and the page shows that email's address, never the person's current one, so whoever reads an address the person left can't learn the new one. "Subscribe again" works only from the address the person still holds and never for a blocked one; it clears the opt-out, even while a double opt-in waits (the link proves the address), and leaves the person's lists as they are, so a list an agent took them off stays off. The confirmation page names no address at all.
- **The pages and the confirmation email speak the subscriber's language only when the package's strings exist in it** (`PageLocale::pick()`), else the app's: a language with no strings would show English laid out right to left.
- **Throttles**: the GET pages through the `throttle` alias per visitor (apps rebind it, for instance to treat an IPv6 /64 as one visitor); the POSTs through the `campaigns.links` limiter per link, never per visitor, since mail apps post many people's one-clicks from a few servers.
- **A test email's link opens the real page and changes nothing** but the test's `unsubscribed_at`.
- **An unsubscribe counts against the email only when it opted the person out** (`campaign_messages.unsubscribed_at`, conditional, first time only), and its consent record carries the message's uuid in `meta` and the source `one_click` or `unsubscribe_page` (`UnsubscribeAction`'s constants), so a campaign's numbers can tell the mail apps' one-click from the page.
- **Links start with `campaigns.url`** (`Support\Links`), never the request's host or `route()`'s root, since queued jobs build them and delivered mail must keep working after the app's main domain moves.
- **The double opt-in email goes out from a job that carries only the subscription's id**: the job makes the token and stores its hash, so the raw token never sits in a queue payload, a failed job or an error report. An address gets one such email a day (`campaign_subscribers.confirmation_sent_at`, claimed by a conditional update, never a cache key, which a deploy's cache clear would reset), a blocked address none, and none at all while `campaigns.enabled` is off. Each email's link replaces the previous one; a send that throws puts the earlier link back and frees the address's day.
- **An address change takes the person's sent mail with them** (`ChangeEmailAction` moves the old row's messages to the person's new row, keeping the old address on them), so an old email's unsubscribe link still reaches the person. A campaign that reached both rows keeps the old row's email where it was. The person's engagement goes too: the latest of each engagement date and the earliest `first_mailed_at`, so a move never makes a reader look silent.
- **An import never undoes what the app knows** (`ImportContactsAction`): it joins through `SubscribeAction` with no choice of the person's (it drops the context's `accepted`, whatever the caller passed), so it never clears an opt-out or a block or changes a list subscription that exists; it gives a subscriber linked to an app record no details (the list source owns them, and its next sync would put them back) and any other subscriber, when the import has a list, only the details and custom fields it lacks; engagement dates only move forward. An import with no list writes only opt-outs, blocks and engagement. Its opt-outs and blocks go through `OptOutAction` and `BlockAction` with the basis `imported` unless the context names another.
- **An address kept only so it is never mailed gains nothing from an import** but the import's own block or opt-out: blocked or opted out, linked to no record and on no list, which is what a person who left looks like (`ForgetSubscriberAction`), so they get no details back. An opt-out or block imported with no list makes such a row too, holding only the address.
- **An import is one transaction per row, and a dry run is the real run rolled back**; an address that appears twice counts once, so the dry run's numbers are the real run's, but a later row's opt-out or block the first lacked is still added (its dates are dropped, so a bad one can't cost it that), so none is lost; a row that found no subscriber and made none leaves the address to the next row. The row's first read is a locking read by address, before any plain read, so a person deleted or moved at that moment is seen as they are after it (a lock by id after a plain read would land on whoever took the row's place, and MySQL's snapshot would still show the deleted row). The row runs in Laravel's `transaction()`, a dry run throwing `RolledBackRow` to roll it back, so a deadlock runs it again at the top level and is handed back with the transaction count right inside a caller's transaction, where MySQL has dropped the savepoints. A database error's message carries the SQL with the row's address, so every value is checked before the write (engagement dates before 2 January 1970, an export's `0000-00-00` among them, or in the future; text that isn't UTF-8 or holds a NUL), and a `QueryException` that still happens stops the import with only its SQLSTATE. Problems name a row by its number, never its address, since an agent's chat shows them.
- **Tiers and the sunset are worked out, never stored** (`Support\Engagement`): engaged or active by the latest of the last human open, click and app activity; sunset when the later of that and `first_mailed_at` (the first campaign email the app sent the address) is older than `sunset_months`. So any engagement, `recordActivity()` included, ends a sunset at once, and an address the app never mailed is never sunset, however old its imported dates. The PHP and SQL definitions sit side by side and a test checks they agree on every database.
- **The engagement queries compare each column on its own**, never through `GREATEST()` or a `NOT`: MySQL's `GREATEST()` is NULL when any argument is, PostgreSQL's skips NULLs, and `NOT` over a NULL comparison drops the row. Their cutoffs drop fractional seconds, as stored timestamps do.
- **Filters target; `mailable` decides who may be mailed.** `SubscriberFilters` narrows (a list filter counts only `subscribed` unless asked, so a pending double opt-in, or a record that can't be on its dynamic list now, isn't on it) and refuses an unknown filter or list key rather than returning nobody; opted out, blocked and sunset stay a separate scope, so a preview can count each reason.
- **A named audience may query the app's own records**: `Campaigns::audienceSubscribers()` turns it into a subscriber query through the record link, as a subquery, never by loading ids, after validating its parameters with its own `rules()`.
- **A campaign's audience is its target lists, narrowed by every other part** (`AudienceDefinition`): a named audience, a saved audience (read when the campaign starts, so a change reaches every campaign not yet started), filters, the people named by subscriber id or address (one set) and app record ids (by the key of the dynamic list whose source holds them, checked against its key type, since PostgreSQL answers a text id for an integer column with a database error) each narrow, with AND. Only `subscribed` subscriptions count. Addresses become subscriber ids when the audience is set, so a stored audience holds no address, only how many matched nobody; a set of people given that names nobody is stored as `[]` and reaches nobody, never everyone (null means none was given). Each part names at most 10,000.
- **One query for the preview, the count and the freeze** (`CampaignAudience`): subscribers are picked through subqueries, never a join to their subscriptions, so a person on two lists is one row; the preview and the freeze read the same rows, a chunk at a time by id, so the number an agent confirms is the number frozen. The preview's dropped reasons don't overlap (blocked, then opted out, then sunset), so they add up.
- **Starting is a claim, then a queued freeze** (`StartCampaignAction`, `FreezeCampaignAction`): the start checks what it can in the call, then moves the draft to `starting` under the campaign's row lock (the lock `AddRevisionAction` and `UpdateCampaignAction` take, so an edit lands before it or is refused) and queues the freeze. The freeze is one transaction: the email, the messages and the move to `sending` or `scheduled`; a recipient count other than the one given rolls all of it back and returns the campaign to `draft` with `start_error` saying why. Nothing changes a `starting` campaign but a cancel, which the freeze finds and leaves alone. Each start has a run id (`campaigns.start_run`) its job carries, so a job left over from an earlier start neither freezes nor hands back a newer one. A freeze job that dies hands the campaign back from `failed()`; one lost without running doesn't (the pump's sweep is still to come). A database error in the freeze is rethrown as a `CampaignsException` holding only its SQLSTATE, never chained, since its message lists the inserts' values, recipients' addresses among them. The freeze's one transaction holds the campaign's row and, on MySQL, a shared lock on each recipient's subscriber row it has inserted a message for, so for its length a cancel or a pace change, and an update of those subscribers (`recordActivity()` on a sign-in), wait: seconds for a few thousand recipients, more for a very large audience.
- **The send order is in `campaign_messages.position`** (an `unsignedBigInteger`): the tier in steps of `FreezeCampaignAction::TIER_STEP` (engaged, active, silent), then the rank within the tier times the number of mailbox providers, plus the provider's place, so providers take turns. The tier comes from `Engagement::tier()` per row, the PHP twin of the SQL, since the freeze reads by id. Gaps are fine: only the order counts.
- **The email that goes out is frozen with UTM tags** on links to the app's own sites (`campaigns.utm.hosts`, else the hosts of `APP_URL` and `campaigns.url` without `www.`, and their subdomains): a copy of the current revision with `frozen_from_id` naming it and its check results carried over, or the current revision itself when nothing needed a tag. A link holding any `utm_` parameter or a placeholder stays as written; a given plain text is tagged too, a generated one generated again. A duplicate copies `Revision::authored()`, never the tagged copy, whose links would carry the old campaign's key for good. A campaign's `utm` is null for the defaults (the config's source and medium, its key as `utm_campaign`), `[]` for none, or the tags that replace the defaults.
- **A pace stores only what was given** (`campaigns.pace`), and `Pace::resolve()` fills the rest from the config when it is read, so an unset value follows the config. A null `daily_cap` or `sending_hours` given on purpose means none. A slow-down (`ChangePaceAction` with `faster: false`) refuses any change `Pace::isFaster()` sees: a higher number, a lifted or higher cap, or sending hours that reach a minute the old ones didn't (a new timezone counts), so the slower path never stands in for a speed-up.
- **A scheduled campaign is frozen when it is scheduled** and waits in `scheduled`; paused before its time, it goes back to waiting when resumed, or starts if its time has passed. `CampaignStartedEvent` fires when a campaign reaches `sending`, never at scheduling.
- **While `campaigns.enabled` is off**, starting, scheduling, resuming, speeding up and test emails are refused; pausing, cancelling and slowing down work, since stopping must never wait. Cancelling leaves a campaign's messages as they are, the unsent ones `pending`, so its numbers show how far it got.
- **A send's answer decides what happens to the message, by transport fact first, then status, never by the provider's words** (`MailgunProvider::failure()`): a connection lost before an answer, a 504, a 400 or anything unread is `Unclear`, since the provider may have the message and it must never go twice; only a 429, 500, 502 or 503 is `NotAccepted` (taken nothing, may go later); a 401, 403 or 404, a campaigns mailer that can't be built, or one on another transport is `DomainRefused` (nothing more can go from the domain until someone acts). Mailgun's 429 says "not allowed to send" too, so a text match would pause a domain over a rate limit. `SendFailed`'s message never holds an address (`SendFailed::scrub()`) and never chains the transport's exception, whose message quotes the answer.
- **The Mailgun driver sends only through `MailgunApiTransport`** (the mailgun transport with `'scheme' => 'api'`), or the log and array mailers, which deliver nothing: the MIME and SMTP transports would put the `o:` options in the email as headers. Every message carries both `o:tracking-opens` and `o:tracking-clicks` as `yes` or `no`, so the domain's own tracking setting never decides, and opens are off for a subscriber in `campaigns.no_open_tracking_countries` (France by default) whatever the campaign says. Mailgun's id is stored without its angle brackets, as its events give it.
- **A campaigns Mailgun mailer with no `client` options gets `['timeout' => 10, 'max_duration' => 30]`** at registration (`CampaignsServiceProvider::boundMailgunClient()`): Symfony's client only times out a quiet connection, and a send job must end before its own timeout.
- **A campaign's message is built from its campaign's frozen revision, a test email from the revision it was made of** (`campaign_test_sends.revision_id`), so the web version shows what was sent after the draft moves on. A recipient gets their locale however written, else its language, else another version in that language, else the default (`Revision::contentFor()`).
- **Test emails go to `campaigns.test_addresses` only**, checked when queued and again in the job; one per address and language, at most 25 a call; a draft's current revision, a started campaign's frozen one. They carry their uuid as `campaign-test` (a message's is `campaign-message`) and the tag `campaigns-test`, so the provider's events and numbers never mix them with a campaign's. The job makes the token and claims the row by a conditional update on a null `token_hash`, so a duplicate sends nothing; a failure is written to `failed_at` and `failure` for the agent that asked.
- **The web version renders an agent's uploaded HTML on the app's origin**, so it answers with a `sandbox` Content-Security-Policy (no scripts, no same-origin, no forms; popups allowed so links open) and changes nothing. A forgotten recipient's or an unknown token's link shows the invalid page.
- **The pump claims, then hands to the queue** (`PumpCampaignsAction`): pending ids are read in `position` order, then claimed by an update that takes only rows still pending, writing the run's claim id and `claimed_at`, and only the rows carrying the run's id get a `SendMessageJob`, so two runs at once never hand one message out twice. Each campaign is worked in its own try, a failure reported and tried again next minute. Nothing runs while `campaigns.enabled` is off, scheduled starts and lost-start hand-backs included.
- **An event a pump or a send job dispatches carries a campaign found on its own**, never one from a list it read: a model loaded among several refuses lazy loading under strict models, so a listener reading its relations would fail. A listener that throws is reported, and the run goes on with the other campaigns.
- **The allowance is counted from the messages** (`Sending\Allowance`): claims whose `claimed_at` falls in a window and whose message isn't `pending` or `skipped` (indexed on `campaign_id, claimed_at, status`; `confirmation_sent_at` is indexed for the domain's count). It is the least of the per-minute rate (halved, rounded up, while `rate_halved_until` is ahead) less this calendar minute's claims; the day's volume (`Pace::dayVolume()`, day n being the nth 24 hours from `pace_started_at`) less that day's claims; the domain's cap less its last 24 hours of claims across every campaign on it (paused, completed and cancelled ones too) and the double opt-in emails sent in them; and nothing outside the sending hours (`Pace::isSendingTime()`, in the pace's timezone). The domain's cap is its `campaigns.domain_daily_caps` entry, else the smallest daily cap among its sending campaigns, else none; a campaign's domain is its From address's (`Campaign::sendingDomain()`).
- **The send job takes its message from `queued` to `sending`** in one conditional update on its id, its claim id, the status, a claim no older than `SendMessageJob::CLAIM_EXPIRES` (15 minutes) and its campaign still `sending` (with sending switched on), writing the token's hash in the same update; otherwise a message still queued under its claim goes back to `pending`, so a job that waited out a stopped worker never sends past the pace or the sending hours. The send-time checks (the subscriber exists and still holds the message's address, `isMailable()`, still subscribed on one of its `list_ids`) and an email the composer can't build skip it. Accepted: `sent` (from `sending` or `unknown`, since `failed()` may have marked a slow job), and the subscriber's `first_mailed_at` set once (not even tried once set: on MySQL the update locks the row before its check, and would wait on a freeze holding its recipients' rows). `NotAccepted`: back to `pending`, and `rate_halved_until` ten minutes ahead. `DomainRefused`: back to `pending`, and every sending or scheduled campaign on the domain paused (`automatic`). `Unclear`, or anything else a provider throws: `unknown`, with the `SendFailure` value in `failure_reason` and the status in `failure_code`. A job that dies leaves a `queued` message `pending` and a `sending` one `unknown`.
- **A campaign completes in one conditional update** once no message is `pending`, `queued` or `sending`, so a pause landing at the same moment is never overwritten. Its `sent` and `unknown` messages can still change after that (deliveries, bounces, the reconciler).
- **Queued messages older than five minutes stop a campaign's claims** and fire `CampaignQueueStalledEvent` on every run while they last, so a stopped worker never gets a pile of jobs waiting for it.
- **A start still `starting` past `FreezeCampaignJob::TIMEOUT` plus ten minutes is handed back to a draft** by the pump (`FreezeCampaignAction::refuse()`), since a freeze job lost without running never reaches its `failed()`. Nothing but a cancel writes a `starting` campaign, so its `updated_at` is when the start claimed it.
- **The pump is scheduled every minute with `withoutOverlapping(5)`** while `campaigns.schedule` is on, its lock on `campaigns.cache_store` through a `CacheEventMutex` of its own, so the app's other scheduled commands keep theirs.

## Extension points

- `Mozex\Campaigns\Contracts\CampaignProvider` (`campaigns.provider`: `mailgun`, `fake` or a class): the sending provider. An app's tests set `fake` and read `FakeProvider::sent()`, or script failures with `failNext()`.
- `campaigns.no_open_tracking_countries`: where opens are never tracked.
- `Mozex\Campaigns\Contracts\ListSource`: an app model as a dynamic list (`campaigns.list_sources`), with `isEligible()` for the app's own rule and `fields()` for the details kept in step.
- `Campaigns::recordActivity($record)`: the app's sign-ins, purchases and the like, as engagement.
- `Mozex\Campaigns\Contracts\Audience` (`campaigns.audiences`): a named audience with its parameters (declared as an MCP tool declares its input), their validation rules and a query on the app's records or on subscribers.
- `Mozex\Campaigns\Contracts\AgentResource` (`campaigns.resources`): read-only data agents may read a page at a time, such as the app's products.
- `ImportContactsAction`: the app's own import commands (from another email service, a chat tool, a shop) call it with `ImportedContact` rows.
- `campaigns.engagement`: the tier windows and the sunset period, `null` to never sunset.
- `SendConfirmationAction`: the app calls it after `SubscribeAction` leaves someone pending on a double opt-in list, such as a newsletter form's sign-up. It sends nothing while `campaigns.enabled` is off, so sign-ups made then need it called again once sending is on.
- The pages', the confirmation email's and the footer's views (`campaigns-views`) and English strings (`campaigns-translations`) publish, so an app restyles them and adds its languages; `campaigns.name` names the app in them.
- The actions resolve through the container, so an app can bind a subclass.
- `Fetching\StaticHostResolver`: an app's own tests bind it in place of `HostResolver`, so the link checks and image fetches never look up real hosts.
- `CampaignStartedEvent`, `CampaignPausedEvent` (with the reason, and `automatic` true when the package paused it itself) and `CampaignCompletedEvent`, dispatched after commit; `CampaignQueueStalledEvent` (each minute while a campaign's queued messages aren't picked up).
- `campaigns.schedule` off: the app schedules `campaigns:pump` itself.
- `campaigns.utm`: the default UTM source and medium, and the hosts whose links are tagged.

## Testing

- `TestCase` runs the migration stub on Testbench's in-memory SQLite before each test, with foreign keys turned on (Testbench leaves them off; Laravel's own SQLite config turns them on) and strict models (apps commonly run them).
- `useDatabase($driver)` in `tests/Pest.php`, with the `databases` dataset (`sqlite`, `mysql`, `pgsql`), moves a test onto a real server's `campaigns_testing` database: it creates that database if needed, drops every table in it and runs the stub. Locally it skips when no server answers; on GitHub Actions it fails instead, since CI starts both servers. The defaults match CI's service containers; `CAMPAIGNS_TEST_MYSQL_*` and `CAMPAIGNS_TEST_PGSQL_*` (`HOST`, `PORT`, `USERNAME`, `PASSWORD`) point at others.
- Anything database-specific (claims, locks, column lengths, JSON) gets the `databases` dataset.
- The install tests delete the config and migration files they publish into Testbench's app, before and after each test.
- Laravel skips its CSRF check under unit tests, so the one-click test binds the class the kernel's `web` group lists (`ValidateCsrfToken` on Laravel 12, `PreventRequestForgery` on 13) to a subclass that checks anyway, and proves an app's own web form gets 419. `Route::middlewareGroup()` in a test changes nothing: the HTTP kernel puts its own groups back on the router for each request.
- `sentMessage()` in `tests/Pest.php` makes a sent message with the raw token of its links; `sendFromExample()` configures a sender on `news.example.com` and turns sending on, `subscriberOn()` makes a subscriber on lists, and `campaignEmail()` one locale's email that meets the rules. `sendingCampaign()` starts a campaign on a list of new subscribers, frozen and sending, through the fake provider (`fakeProvider()`). Fake only the send jobs (`Queue::fake([SendMessageJob::class])`), so a campaign started after the fake still freezes, and travel to UTC instants.
- `testImage()` gives tiny real images (CI has no image extension to make one), `zipOf()` builds a zip (links and encrypted entries included) in a temporary file it deletes, and `resolveHosts()` binds `StaticHostResolver`, so a fetch under `Http::fake()` never makes a real DNS lookup. Fake the asset disk with an https `url` (`Storage::fake('public', ['url' => 'https://...'])`), since a fake's default address is relative and every image would be refused.
- `tests/Fixtures/Member` (a `members` table, created in `TestCase::runMigrations()` so the real-server runs get it too) and `MemberList` stand in for an app's accounts and their list source; `MembersInCountry`, `RecentContacts` and `MemberDirectory` for its audiences and a resource. PHPStan analyses the fixtures, since it checks a trait only through a class that uses it.
- The Mailgun driver's tests swap a `MailgunApiTransport` over Symfony's `MockHttpClient` into the campaigns mailer (`mailgunMailer()` in `tests/Sending/MailgunProviderTest.php`) and read the posted form fields, since `Mail::fake()` skips the transport that turns tags, metadata and `o:` options into Mailgun's fields. Never test a refused transport against a real one: its broken form would reach a real server.
- JSON columns come back in the database's own key order (MySQL and PostgreSQL sort keys), so a test compares a stored map with `toEqual()`, not `toBe()`.

## Development notes

- `CHANGELOG.md` is generated from GitHub releases by the changelog workflow. Never edit it by hand.
- The PHP floor is 8.2: no typed class constants (`public const string X`) and no `new Foo()->bar()` without wrapping parentheses. PHPStan's `type_coverage.constant` is 0 for that reason.
- Larastan reads columns only from `.php` migrations, never the `.php.stub`, so each model lists its columns as `@property` lines. A new column gets its line in the same change, or code reading it fails PHPStan.
- Read `campaigns.domain_daily_caps` as a whole map: its keys are domains, and the dots in them make `config('campaigns.domain_daily_caps.'.$domain)` find nothing.
- Eloquent's `Table`, `Fillable` and `Hidden` attributes don't exist on the Laravel 12 floor, so models set `$table`, `$fillable` and `$hidden` as properties. `UseFactory` does exist there.
